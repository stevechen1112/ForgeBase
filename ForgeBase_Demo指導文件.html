Demo 的運作原理

這個 Demo 不是靜態 UI 展示。前台官網的每一次點擊、瀏覽都會即時寫入後台資料庫，管理後台即時呈現。換句話說：

你從前台扮演買家來瀏覽，後台就會出現對應的事件、分數變化、訪客記錄。

但「剛清空的後台」效果很差——訪客列表空白、RFQ 收件箱是零，完全無法說明系統在做什麼。正確的做法是：

[Demo 前] 跑 Seed 腳本 → 後台已有歷史軌跡（看起來系統已在運作）
[Demo 當下] 現場瀏覽前台 → 後台即時出現新事件（現場感）

服務已部署於雲端，無需本地啟動。直接瀏覽器確認以下三個網址可正常存取：

  • 前台官網：https://mitselect.com
  • 管理後台：https://mitselect.com/backend

步驟四：Demo 當下的「現場感」操作

Demo 期間最有說服力的時刻：客戶親眼看到系統即時記錄行為。

  1. 打開一個新的無痕視窗（⌘ + Shift + N），開啟 https://mitselect.com
  2. 瀏覽幾個產品頁、展開一個 FAQ、點擊 CTA 按鈕
  3. 切回管理後台 → 追蹤 → 事件列表 → 畫面重新整理
  4. 剛才的行為立即出現在後台，並帶著 intent 分數變化

第一部分：Capture Layer — 內容與頁面系統（20 分鐘）

1-1 前台官網整體瀏覽

操作：開啟 https://mitselect.com

展示重點： - 首頁 Hero、產品分類卡片、應用場景摘要、認證展示 - 主推產品區塊（「Featured Products」）— 當後台有任一產品被標記為主推時自動出現，優先展示高優先度產品 - 麵包屑（Breadcrumb）自動產生 - 導覽到產品分類頁 /products/ - 導覽到單一產品詳頁 /products/{category}/{product}/

建議話術： > 「這是訪客看到的前台。每一頁都是依標準化頁型建出來的，不是自由排版，這樣 SEO 的 structured data、breadcrumb、internal link 才能自動運作。首頁的主推產品區塊是後台控制的——業務想把哪個產品推到第一眼，不需要改程式，在後台點一下星星就完成。」

1-2 管理後台 — 產品資料管理

操作：切換到 https://mitselect.com/backend → 登入 → 產品管理

展示重點：

  1. 產品列表 — 可依分類、狀態（草稿/已發布/封存）篩選
  2. ⭐ 主推產品切換 — 每筆產品旁有星星按鈕，點一下即標記為「主推」（金色星星），前台首頁的 Featured Products 區塊立即反映；再點一下取消。無需儲存按鈕，即時生效。
  3. 新增或開啟一個產品，展示欄位：
    • 產品名稱、型號（model_number）
    • 規格鍵值對編輯器（名稱 + 值 + 單位）
    • 圖片上傳（支援多張）
    • 富文字產品說明
    • 所屬分類選擇
  4. Entity 關聯面板 — 展示可直接在產品上設定：
    • 關聯應用場景
    • 關聯認證
    • 關聯 FAQ
    • 設定替代料號（雙向自動建立）

建議話術： > 「產品資料不只是填名稱和規格。我們讓每個產品都能關聯到它適用的應用場景、認證、FAQ，這些關聯會自動產生頁面上的內連，也是 AI 生成文案時的知識來源。孤立的資料在這個系統裡沒辦法發揮作用。」

1-3 內容策略地圖（Page Brief 系統）

操作：管理後台 → 內容策略 → Page Brief 列表

展示重點：

  1. Page Brief 狀態流程：

    草稿 → 審核通過 → 生成中 → 已完成 → 已發布

  2. 開啟一個既有 Brief，展示欄位：

    • 頁面類型（產品詳頁 / 應用頁 / FAQ 頁…）
    • 目標市場（美國、德國、日本…）
    • 目標客群（採購、工程師、代理商…）
    • 搜尋意圖（比較型、規格型、採購型…）
    • 主要關鍵字群
    • Primary CTA 指定

建議話術： > 「在 AI 生成任何文案之前，我們強制要求先定義這一頁為什麼存在。目標市場是誰、要捕捉什麼搜尋意圖、這一頁的轉換目標是什麼。不允許先生成再期待流量，這樣的設計讓每一頁都有商業目的。」

1-4 AI 內容生成

操作：管理後台 → 找到一個 Approved 狀態的 Page Brief → 點擊「生成初稿」

展示重點：

  1. AI 根據 Brief + 產品規格資料生成結構化初稿，包含：
    • SEO title（60 字上限，關鍵字置前）/ meta description（155 字，含行動短語）
    • 產品全文說明（依 Brief 目標字數，含 H2/H3 標題結構與關鍵字佈局）
    • FAQ 建議（3–5 個，問句格式符合 Google PAA 篩選規則）
    • CTA 主標題 / 副標題
    • 內連建議（internal_link_suggestions）：AI 同步建議此頁應連結到哪些相關產品、分類或應用頁，附建議錨文字與理由
  2. 每個欄位旁邊有狀態標記：AI 生成 / 已人工審核 / 人工撰寫
  3. 可逐欄修改，也可「重新生成」整段

建議話術： > 「AI 不是用來一鍵發布的，是用來降低內容建置成本的加速器。生成出來的是初稿，每個欄位都有審核狀態，強制人工確認後才能發布上線。」

「生成的文案從一開始就內建 SEO 品質標準——標題不超過 60 字、meta description 有行動短語、內文有清楚的 H2 結構、FAQ 問句格式符合 Google PAA 規則。這不是人工事後補救，是生成時就直接做對。」

展示 AI 生成限制： > 「我們不提供自由 prompt——因為那樣生成的文案品質不穩定、跟業務目標脫節。這個系統的 AI 只在有 Brief 和結構化資料的基礎上運作。」

1-5 頁面發布與 SEO 基礎設施

操作：管理後台 → 頁面管理 → 選一個完成的頁面 → 發布

展示重點：

  1. 發布後前台自動上線 — 訪問對應 URL
  2. SEO 自動輸出，在瀏覽器開發工具 Sources / Elements 確認：
    • <title> 與 <meta name="description"> 正確填入
    • <link rel="canonical"> 自動生成
    • JSON-LD Structured Data（Product schema 或 FAQPage schema）
  3. 取消發布（Unpublish）：
    • 頁面狀態回到草稿
    • noindex 自動加回，搜尋引擎不會二次索引

建議話術： > 「技術 SEO 是基礎設施，不應該是人工設定的。canonical、structured data、noindex 這些全部系統自動處理，內容人員只需要專注在文案品質上。」

1-6 預覽功能（草稿預覽）

操作：管理後台 → 找一個草稿狀態的頁面 → 點「產生預覽連結」

展示重點： - 系統產生一個有時效性的預覽 Token（1 小時有效） - 複製連結在前台開啟 → 顯示醒目的 ⚠ PREVIEW MODE 警示橫幅 - Token 過期後再開啟 → 自動導向 404，不會洩漏草稿內容

建議話術： > 「內容還在草稿時，客戶或主管想先看效果，可以用這個安全預覽連結，時效過了就失效，不用擔心沒完成的頁面被搜尋引擎抓到。」

1-7 SEO 稽核工具

操作：管理後台 → SEO 稽核

展示重點：

  1. 總覽 Dashboard：全站 SEO 健康分數
  2. On-Page 稽核：逐頁列出缺少 meta description、title 過長／過短、h1 缺失等問題
  3. 關鍵字蠶食偵測（Cannibalization）：自動找出多個頁面搶同一關鍵字的問題，建議整并或差異化方向
  4. 機會列表（Opportunities）：依流量潛力排列尚未最佳化的頁面，並提供可執行的建議
  5. 一鍵最佳化（AI Optimize）：對選定頁面執行 AI 改善（title、meta description、內文建議）

建議話術： > 「大部分製造商的官網有幾十個產品頁，手動管理 SEO 根本做不到。這個 SEO 稽核工具會主動告訴你哪些頁面有問題、哪些頁面有機會，而且你自己的頁面在搶同一個關鍵字這種蠶食問題，人工根本找不到，系統自動監控。」

第二部分：Intent Layer — 訪客意圖追蹤（18 分鐘）

2-1 First-Party 事件追蹤

操作：開啟前台任一頁面，同時在管理後台 → 追蹤 → 事件列表 → 即時重新整理

展示重點：

展示以下事件自動被記錄（不需要 GA）：

操作 自動觸發的事件
進入首頁 page_view
進入產品分類頁 category_view
點擊進入產品詳頁 product_view（附帶 product_id）
點擊展開 FAQ faq_expand
點擊下載規格書 spec_download
點擊 CTA 按鈕 cta_click
開始填寫 RFQ rfq_start

建議話術： > 「這是我們自己的 first-party 事件，不是 Google Analytics 的 session。這些事件帶著 visitor_id、product_id、page_type，讓我們能算出每個訪客的商業意圖分數，而不只是看頁面停留時間。」

2-2 意圖評分系統（Intent Scoring）

展示重點：

評分規則即時展示：

行為 分數
瀏覽產品詳頁 +3（重複瀏覽 +2）
瀏覽應用頁 +4
展開 FAQ +6（展開 3+ 個 +4）
查看比較頁 +6
下載規格書 +8
點 Primary CTA +8
開始填 RFQ +15
送出 RFQ +30

意圖階段（Intent Stage）：

分數 階段 說明
0–9 ❄️ Cold 只是瀏覽
10–29 🟡 Warm 有互動行為，進入再行銷
30–59 🔥 Hot 明確產品興趣，觸發業務 Alert
60+ ✅ Sales-Ready 直接跟進，通知業務優先處理

展示衰減機制： > 「分數不是只增不減。7 天沒有活動，分數乘以 0.8；14 天乘以 0.5；30 天乘以 0.2；60 天歸零。這樣業務名單永遠是最新鮮的。」

2-3 訪客詳頁（Visitor Timeline）

操作：管理後台 → 追蹤 → 點進一個 Hot 或 Sales-Ready 的訪客

展示重點： - 事件時間軸：看他這幾次 session 都看了哪些產品、哪些應用、有沒有展開 FAQ - 當前 intent_score 與 intent_stage - 關聯的 Contact（若曾填過表單） - 來源頁 source_page 記錄（知道他是從哪個行銷活動或搜尋關鍵字進來）

建議話術： > 「業務不需要靠直覺猜客戶要什麼。這個時間軸直接告訴你：這個人看了哪個產品分類、在哪個應用頁停留最久、下載過規格書。業務跟進時就有具體的談話切入點。」

2-4 帳戶智能（Account Intelligence）⭐ B2B 核心賣點

操作：管理後台 → 帳戶 → 帳戶列表（依活動日期排序）

展示重點：

  1. 公司層級追蹤：系統不只追蹤「一個訪客」，而是追蹤「一家公司」的多個瀏覽者行為加總
  2. IP 反查公司：對未填資料的匿名訪客，系統可依 IP 位置推測公司名稱與產業
  3. 帳戶 Insight 面板（點進一個帳戶）：
    • 該公司共有幾位不同訪客造訪
    • 累計瀏覽了哪些產品類別
    • 最高意圖訪客的 intent_score
    • 是否已有關聯的 Contact 或 RFQ
  4. 帳戶層級 Enrichment：可呼叫外部資料庫補充公司規模、產業、所在地

建議話術： > 「工業 B2B 的採購決策不是一個人做的。一家德國汽車零件廠可能有採購、工程師、主管三個人分別在不同時間看你的頁面——我們能把這些軌跡歸到同一個帳戶。業務不只能看到訪客，還能看到『哪家公司』這個月反覆造訪、還沒詢價。這就是業務主動出擊的依據。」

第三部分：Conversion Layer — 詢盤閉環（25 分鐘）

3-1 RFQ 詢價前台流程

操作：開啟前台 https://mitselect.com/request-quote 或從產品頁點擊詢價 CTA

展示重點：

  1. 從產品頁進入 RFQ：產品欄位自動帶入（無需重複選擇）
  2. 表單欄位：姓名、公司、Email、國家、職稱、感興趣產品、應用場景、數量、規格需求、採購時程
  3. 同意聲明（必填）
  4. 表單草稿自動儲存：中途關閉瀏覽器，重新打開草稿還在
  5. 送出後確認頁：顯示 RFQ 編號（RFQ-20260315-001）

建議話術： > 「從產品頁直接點詢價，產品欄位自動帶入，降低填表摩擦。表單會記住草稿，買家不怕中途打斷。送出後業務端馬上會收到通知。」

3-2 下載門欄（Download Gate）

操作：前台產品頁 → 找到規格書下載按鈕 → 點擊

展示重點： 1. 跳出 Modal 要求留下基本聯絡資料（姓名、Email、公司） 2. 送出後直接提供下載連結 3. 後台自動建立/更新 Contact 記錄 4. spec_download 事件同步寫入，intent 分數 +8

建議話術： > 「下載規格書是高意圖行為，我們把它變成一個留資機會。填完資料才能下載，而且系統自動記下他下載的是哪個產品的文件，這個訊號直接反映在意圖分數上。」

3-3 管理後台 — RFQ 收件箱

操作：管理後台 → 轉換 → RFQ 列表

展示重點：

  1. RFQ 狀態追蹤：

    新建 → 已指派 → 處理中 → 已報價 → 成交 / 失單 / 過期

  2. 指派業務：點擊 RFQ → 指派給對應業務人員

  3. 優先度標記：意圖分數 ≥ 30 的 RFQ 自動標記高優先（🔥）

  4. 開啟 RFQ 詳頁，展示完整資訊：

    • 聯絡人資料 + 公司
    • 感興趣的產品列表

    • 送出時的意圖分數（intent_score: 42, stage: Hot）

Demo 常見 Q&A

Q：這和一般 CMS（WordPress / Webflow）有什麼不同？ > A：一般 CMS 只管前台頁面，沒有意圖追蹤、沒有 RFQ 閉環、沒有再行銷受眾同步。ForgeBase 是把 Capture、Intent、Conversion 三層整合在一個系統裡，官網本身就是業務工具，不只是型錄。

Q：AI 生成的內容品質可靠嗎？ > A：AI 生成的是「基於規格資料的結構化初稿」，不是憑空捏造的文案。每個欄位有審核狀態標記，未經人工確認不能發布。這個設計確保品質底線，同時把建置時間縮短 60–70%。

Q：我們不會 SEO，系統能自己處理嗎？ > A：技術 SEO 部分（canonical、structured data、sitemap、robots、breadcrumb）全自動。內容 SEO 部分（關鍵字、意圖對齊）由 Page Brief 系統引導操作，不需要有 SEO 背景。

Q：系統收到的詢盤資料安全嗎？ > A：所有資料存在你們自己的資料庫，不走任何第三方平台。Webhook 有 HMAC 簽章。訪客識別用 first-party cookie，不依賴第三方 cookie。

Q：可以先從局部導入嗎？ > A：可以。支援三種導入模式： > 1. 標準導入：全站一次上線 > 2. 過渡導入：用子網域先接管 RFQ / 產品頁 > 3. 嵌入式導入：在現有網站插入表單、追蹤元件，先驗證成效
